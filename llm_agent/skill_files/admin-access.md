---
name: admin-access
description: Give an app one protected admin that only the owner reaches from Manage app: reuse the project's own admin or provide one, trust the Manage login, remove default passwords.
---
The owner opens the admin with the Open admin button in Manage app after entering the app id and password; inside it they manage the whole app. The platform proxy only lets that session reach the admin paths and adds the header X-Workbench-Admin: 1 to its requests. A visitor can never send that header (the proxy removes it from public requests), and the app listens only on a private port. So the app must trust that header and nothing else for admin access.

A) The project already has an admin (PROJECT.md says which, and the path):
   1. Replace its own login check with the header check. Flask: a before_request on the admin blueprint that aborts 403 unless request.headers.get("X-Workbench-Admin") == "1". Django: a small middleware that, for requests under /admin/ carrying the header, logs in (or creates once) a staff superuser with an unusable password and lets the request through; without the header return 403. Express: a middleware before the admin router: if (req.get("X-Workbench-Admin") !== "1") return res.sendStatus(403). FastAPI: a dependency on the admin router.
   2. Remove every default or hard-coded admin password and any "register first admin" form. Delete default accounts from seed files.
   3. If the admin lives somewhere other than /admin, write admin.json at the project root (no "collections" key, so the project's own pages stay in use): {"paths": ["/dashboard", "/api/admin"]}. List every path the admin pages and admin APIs use. /admin is always protected.
   4. Check it works at 360px wide. If it does not, add a few lines of responsive CSS to the admin templates rather than building another admin.
B) The project has no admin (or only a thin one): the PLATFORM draws the admin dashboard (lists, add, edit, delete, picture and video upload, like a professional app). You never write admin HTML. You write two small things:
   1. admin.json at the project root describing what the owner manages: {"title": "<App> admin", "collections": [{"name": "dishes", "label": "Dishes", "title": "name", "fields": [{"key": "name", "label": "Name", "type": "text", "required": true}, {"key": "price", "type": "price"}, {"key": "photo", "type": "image"}, {"key": "intro", "type": "video"}]}]}. One collection per thing the owner manages (items, categories, orders, bookings, messages, banners, text blocks, users). Field types: text, longtext, number, price, toggle, select (with "options"), date, url, color, image, video, file. Use image/video fields wherever the customer screens show a picture or video, and read that field in the customer pages.
   2. A JSON API in the app's own backend, guarded ONLY by the header check from A1 (403 without X-Workbench-Admin: 1), for every collection: GET /admin-api/<name> returns {"items": [...]} (each with an "id"); POST /admin-api/<name> returns the created item with its id; PUT /admin-api/<name>/<id> returns the updated item; DELETE /admin-api/<name>/<id> returns {"ok": true}. Store the data in the app's database (see data-storage), never in code; the customer pages read the same tables. image/video/file values are web addresses that the dashboard gets from the platform upload: just store the string.
   The app must NEVER open empty: on its first start it fills its tables once (only when empty) with 12 to 20 realistic starter entries with a `sample` flag (store it as a field of the row and return it in the API), so the owner has rows to edit and delete from the first minute; the dashboard shows them as Sample and offers 'Delete all samples'. Orders, bookings and contact messages are saved in the database and listed in their own collection.
   No login form, no password, no admin page. Manage app is NOT where the content is managed: it only deploys, builds and updates the version. After writing it, run check_build and tell the owner to press Update in Manage app, then Open admin.
C) Never put an admin link, button or screen in the pages the customers see, and never in the Android or Windows app. If the user asks for one, say no in one sentence and say where the owner manages it.
D) Never print, log or hard-code an admin password. Do not create another login for the owner.

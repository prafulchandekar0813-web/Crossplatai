---
name: github-ui
description: Build an app from a real open-source project: copy it, read it, keep its framework and structure, change it in place, give it a protected admin and a data choice.
---
Use this for any app with screens before you design from nothing. The copied project IS the app. You are a developer who inherited a codebase: read it first, change the minimum, add only what is missing. Do NOT write a second app beside it and do not move it into another structure.

1) FIND. First library_search with a few words about the app: a project already in the shared library is checked and copies instantly. If nothing fits, github_search 2 or 3 phrasings of the kind of app ("restaurant menu ordering", "booking calendar appointments"). Prefer a permissive licence (the tool only shows those), recent activity, 100+ stars, Flask/FastAPI/Django, plain HTML/CSS/JS or a static site. Pick the best one yourself and tell the user which one and why in two lines. If they say "try another", use the next.
2) COPY. github_clone it. It lands in its own project folder (the repository name) and is safety-checked first:
   - status "blocked": nothing was copied. Tell the user in one line that it was refused for safety and why, then use the next result. Never try the same repository again.
   - status "needs_approval": nothing was copied. Tell the user in plain words what was found (no jargon). They must reply exactly "run anyway" to use it, or "pick another". You cannot approve for them, and you must not call github_clone again until they have said it.
   For a very large repository use subdir to copy only the folder that holds the app.
   The original stays in the shared library; the user's own files are only the ones you change or add. Open and edit just the files the request needs and leave every other file as it is.
3) UNDERSTAND. Call analyze_project on the folder. Nothing in a copied project can be edited before that: the file tools refuse. It writes PROJECT.md. Then read the README, the entry file, the routes, the templates and the data files that the request touches. Tell the user in 3 or 4 plain lines what it is (framework, where its content lives, its admin, its database) and what you will change.
   Then RUN THE ORIGINAL to see it work: install its requirements in the sandbox (python3 -m venv ~/venv && ~/venv/bin/pip install -r requirements.txt) and start it with bash using background=true and the start command from PROJECT.md (it must listen on $PORT). The user sees it in Preview app > Run app, so tell them: "This is the original, before my changes." If it fails, read the log, fix the start command or requirements, and try again a few times; then tell the user the real problem. The sandbox may have no internet: a page that loads data from outside can look empty, which is not a bug in your changes.
4) DATA. Ask the user once where the app should save its data: on our server (SQLite, PostgreSQL, MySQL, MongoDB, Redis or CouchDB) or in their own online database (Supabase, Neon, MongoDB Atlas, Upstash, Firebase, any other). Local SQLite is the default if they have no preference. Then use_skill("data-storage") and follow it.
5) CHANGE IN PLACE. Make the user's request in the project's own files with the patch tools, following its structure and style: its framework stays, its folders stay, new files go next to the files of the same kind. Rename and restyle it so it is clearly this app's own: name, palette, fonts, logo, copy, pictures. Keep the LICENSE and SOURCE.md, and credit it on an About screen ("Based on <owner/repo>, <licence>"). Keep PROJECT.md up to date (the Plan section) as you go.
6) ADMIN. Every app needs one admin, reachable only with Open admin in Manage app. Inside it the owner manages everything in the app; Manage app itself only deploys, builds and updates versions. If the project has no admin, you add admin.json plus the /admin-api routes (the platform draws the dashboard, you never write admin pages). use_skill("admin-access") and follow it. There is never an admin screen inside the installed app: if the user asks for one, say no in one sentence and explain that the owner manages it from Manage app with the app id and password, which is already set up.
7) CONTENT IN THE ADMIN, NEVER EMPTY. Content that is written inside code (menu items, products, prices, hours) must come from the app's database and be editable in its admin. The first start fills the database ONCE (only when its tables are empty) with 12 to 20 realistic starter entries that fit the app (names, prices, descriptions, images that load), marked as sample (a `sample` flag), so the app looks alive and the owner has real rows to edit, delete and add to in the admin on the very first visit. The dashboard shows them as Sample and offers a button that deletes all sample rows. If the repo already has demo data, keep it the same way. Orders, bookings and contact forms are saved in the database and listed in the admin.
8) CHECK. After the last change start it again in the sandbox (bash, background=true) so the user sees the result in Preview app, curl the main page and one API route, read any traceback, fix it, and run check_build on the project folder. The build stays locked until check_build passes and the project has been started in the sandbox with these exact files: run it again after any later edit. Look at it at 360px wide. Only then say it is ready.

If the project is too large or too tangled to change safely, or the hosting cannot run it (analyze_project says so), tell the user in one line and pick another project. Say so rather than forcing a half-working app. If github_search finds nothing usable, say so and continue with the app-design process on your own.
